Status: CLOSED (root cause + evidence)
Date: 2026-09-11
Evidence dir: `SCMessenger/tmp/rca_577fd/`
Scope: why operator sees 3 nodes on Android when only 2 real peers exist

## Verdict (one paragraph)

`577fd171` is **not a live node**. It is the **previous Pixel identity**
(nickname Lucas) that was destroyed by `pm clear` / reinstall. Windows and AWS
never retired it: they keep it in contacts, ledger, history_sync payloads, and
gossip topics. The fresh phone **re-learns** that ghost via ledger/peer-list
exchange, stores it as a ledger row pointing at the **phone's own LAN IP**,
subscribes to `/scmessenger/peer/577fd171…/v1`, and the Dashboard
`loadPeers` unifier paints it as a third node (`online=false`). AWS still
logged live Identify/custody/inbox from `12D3KooWFhvg` (the old libp2p id)
until mDNS expired at **03:21:54Z**. The new phone then **re-advertised** the
ghost topic on connect (04:19Z ByBM, 04:23Z SXDttuet), so other nodes keep
seeing the topic too. This is the identity-rotation / stale-ledger class, not
a second physical device.

This is the feedback loop: ghost → topic subscribe → other nodes "discover"
the ghost topic again.

## Root cause chain (causal, not correlated)

1. **Identity rotation without retirement.** `pm clear`/reinstall mints a new
   keypair. Nothing on Windows/AWS/phone ledger marks `577fd171` dead.
2. **Ledger/peer-list exchange is append-only.** `Sent peer list (N peers)`
   + `Ledger exchange` re-injects historical peer_ids into any new node.
3. **ID canonicalization treats the old pk as a peer_id.** Phone ledger row
   has `peer_id=577fd171`, `public_key=null` — the unification migration
   (`ledger_canonical_hex_migration` from `WFhvg → 577fd171`) collapsed the
   old libp2p id into the **hex pubkey** and kept it as a dialable peer_id.
4. **UI `loadPeers` does not require liveness.** Dashboard unions
   nearby + ledger and renders offline ledger rows as nodes → operator sees
   "3 nodes".
5. **TopicManager amplifies.** Subscribing `/scmessenger/peer/{ghost}/v1`
   makes the ghost visible in other nodes' topic discovery logs.
6. **mDNS/cache decay is slow.** Ghost stayed "live" on Windows via repeated
   inbound connections until 03:21Z / 04:12Z expiries even after the phone
   was wiped.

## What it is NOT

- Not the emulator (emulator identity was `12D3KooWAv9…` earlier; not in this window).
- Not Message Store Unavailable (fresh install started mesh cleanly; that
  earlier bug was a different start-path incident).
- Not a successful dial to 577fd171 on the fresh phone (success_count=0).

| G2 | TopicManager subscribes topics for offline/dead ledger peers | P2 — amplifies ghosts mesh-wide |
| G3 | Dashboard paints ledger-only rows as live "nodes" without online authority | P1 — the exact symptom you saw |
| G4 | Seed-dial still sweeps circuit addrs through dead peer ids | P2 |
| G5 | AWS/Windows contact store accumulates N "Lucas" identities with no supersede | P2 |
| G6 | history_sync payloads rehydrate old sender identities into UI resolution paths | P2 |

## Recommended fixes (do not apply without orchestrator packet)

1. **Ledger TTL / supersede:** on successful Identify of a new identity with
   the same device_id or nickname+same operator, demote previous peer_ids
   that share that device to `retired` and stop advertising them in peer lists.
2. **loadPeers online authority:** require `discovered || ledgerDirect ||
   recent successful dial` before rendering a row as a distinct node; ledger-only
   ghosts go under "Known (offline)" or are hidden.
3. **TopicManager filter:** only subscribe peer topics for identities that
   passed Identify in the last N hours or are currently connected.
4. **Seed-dial filter:** skip multiaddrs whose peer_id has 0 successes and N
   consecutive failures, or whose peer_id is not self-certifying libp2p.
5. **One-time cleanup operator action (safe):** delete stale contacts/ledger
   rows for `577fd171` / `WFhvg` on Windows and AWS after backing up stores.
