## 1. Tailscale: a red herring. The AWS node is simply down.

The operator asked for one always-available AWS node acting as a reliable
friend. A prior handoff recorded the blocker as "100.56.248.69 is a Tailscale
CGNAT address". That diagnosis is wrong.

Tailscale CGNAT is 100.64.0.0/10 (100.64.0.0 - 100.127.255.255).
100.56.248.69 sits below that range -- `ipaddress` confirms is_global=True,
in-CGNAT=False. It is an ordinary public IP inside AWS's 100.56.0.0/14 block.

Measured today: ping 2/2 lost, `curl http://100.56.248.69:9876/health` timed
out (exit 28, http_code 000), `Test-NetConnection ... -Port 9001` = False.

Tailscale appears in only 6 places repo-wide, all documentation, none in
product code. There is no Tailscale integration and no reason to add one.

ACTION: drop Tailscale from the plan. Check the EC2 instance state and the
security group. Per prior lesson (alpha-relay), run the prebuilt image
`testbotz/scmessenger:latest`; never build on the t3.micro.

CAVEAT accepted from review: "no Tailscale in the app" does not settle how the
operator ADMINISTERS the box. If Tailscale was someone's SSH-access plan, that
is an infrastructure choice, independent of the app. It is still not a
connectivity mechanism for peers.

## 2. Share-to-a-friend: two concrete defects

Verified COMPLETE:
- QR generate/scan/parse. Payload built MeshRepository.kt:9311-9354; rendered
  QrCode.kt:22-48; scanned AddContactScreen.kt:302-388; parsed
  ContactImportParser.kt:19-91, which DOES extract a listeners/multiaddr array
  (59-80). Auto-dial on import works: MainViewModel.kt:261-263 ->
  MeshRepository.connectToPeer (6155-6185).
- APK streaming. ApkShareManager.kt:108-156 opens ServerSocket(0) on a dynamic
  port, serves the app's OWN installed APK (sourceDir, 38-40), 15-minute
  lifetime; ApkShareDialog.kt:131-134 renders a QR of the download URL.

Defect A -- HARDCODED DEAD RELAY.
ApkShareManager.kt:114 `val awsRelay = "/ip4/100.56.248.69/tcp/9001"`, baked
into the URL at :129 as `?bootstrap=$awsRelay`. cli/src/main.rs:53 does the
same. That is the dead node from section 1.
This contradicts the doctrine written in the code itself at
MeshRepository.kt:75-83: "there are no dedicated relays and no hardcoded node
addresses ... the static /ip4/100.56.248.69/tcp/9001 fallback ... are removed."
The doctrine was applied to MeshRepository but never to the share feature.
cli/src/main.rs also prints, unconditionally,
`Ledger Inject: [OK] AWS Cloud Node & Local Windows Node linked`
-- a fake success string; nothing is verified before it prints.

SAFE TO REMOVE: cli/src/main.rs:53 only builds the APK-share display URL. The
CLI's real bootstrap is cli/src/bootstrap.rs (SC_BOOTSTRAP_NODES env at :38,
build-time option_env at :49, merge at :106) plus mDNS (config.rs:20-21).
Removing the hardcoded address costs no CLI connectivity.

Defect B -- DEEP LINK CANNOT CARRY THE BOOTSTRAP.
MainViewModel.handleDeepLink (:285-299) extracts only public_key, peer_id,
nickname, identity_id; DeepLinkData (:318-323) has no listeners field. The
`?bootstrap=` parameter is therefore never read. A fresh install cannot
auto-connect, so "scan, install, auto-joined" does not close.

SECURITY NOTE (raised in review, accepted): wiring listeners into the deep link
means the app will accept arbitrary multiaddrs from an untrusted QR or URL.
That is a NEW attack surface and it is the same class of problem as open
finding F2 (unsigned seed import with no verification gate). The fix must
include validation -- reject private/loopback ranges unless explicitly opted
in, cap the number of entries, and rate-limit dials. Do not ship the
convenience without the validation.

## 3. iOS <-> Android pairing (Christy's iPhone vs the Pixel)

Christy runs iOS 0.5.0 build 9 (Info.plist on origin/gpt/v050-ios-release-ready
and .../v050-ios-device-install). Neither branch is merged to main.

GOOD NEWS -- no wire skew. The iOS 0.5.0 branches change NOTHING under core/
(empty diffstat vs main), and relay/protocol.rs:151 PROTOCOL_VERSION = 1 on
both. The 0.5.0-vs-0.4.0 difference is app-layer only. No version gate will
reject the pairing.

BLE -- viable. Identical UUIDs on both sides: service 0000DF01, characteristics
DF02/DF03/DF04, standard 2902 CCCD (android transport/ble/*.kt vs
iOS Transport/BLE*.swift).
CONFIDENCE DOWNGRADED per review: UUID alignment is necessary, not sufficient.
Android and iOS negotiate different default MTUs (roughly 512 vs 185 bytes), so
identity payloads larger than the smaller MTU will fail unless chunking is
correct on both sides. Expect to debug framing, not discovery.

LAN / mDNS -- BROKEN TODAY, and this is the root cause.
Android MdnsServiceDiscovery.kt:77 uses `_p2p._udp`, the libp2p-mdns default,
with an explicit comment that it must match so Rust peers discover us.
iOS mDNSServiceDiscovery.swift:36 uses `_scmessenger._tcp`, and its own comment
at :20 claims this "matches Android's WifiDirectTransport.SERVICE_TYPE".
That claim is literally true -- and it is the bug. iOS matched Android's WiFi
Direct DNS-SD type (WifiDirectTransport.kt:568), a transport iOS can never
join, instead of Android's mDNS type. The platforms advertise and browse
different service types and never see each other.
Compounding: iOS Info.plist NSBonjourServices declares only `_scmesh._tcp`,
`_scmesh._udp`, `_scmessenger._tcp`. iOS 14+ will not browse an undeclared
type, so the plist must also gain `_p2p._udp`.

REGRESSION GUARD (accepted from review -- this is the single most valuable
catch): do NOT simply flip the iOS constant. If two iOS devices currently
discover each other via `_scmessenger._tcp`, flipping it trades a working
iOS-iOS path for a fixed iOS-Android path. Implement DUAL-STACK instead:
iOS browses BOTH `_p2p._udp` and `_scmessenger._tcp`, and declares both in
Info.plist. Roughly 10 LoC instead of 3, and it cannot regress iOS-iOS.

Multipeer Connectivity is iOS-only and, per core/src/mobile_bridge.rs:3426-3427,
maps to TransportType::Internet rather than being wired into the libp2p swarm
-- Multipeer traffic never reaches Android. WiFi Aware and WiFi Direct are
Android-only. Neither is a cross-platform path. Do not plan around them.

## 4. NAT hole-punch is a fake-success stub -- delete it

core/src/transport/nat.rs:442-494 `send_hole_punch_probes()` logs, then runs
`attempt.status = HolePunchStatus::Success;` under the comment "Simulate
success after protocol execution". No UDP socket is created; no packet is sent.
core/src/transport/internet.rs:466 is similarly thin.

Reachable from IronCore::start_hole_punch (iron_core.rs:3510-3527), which also
builds a fresh NatTraversal per call and discards its state.

Mitigating: NOT exposed over UniFFI -- it takes libp2p::PeerId, carries no
uniffi export attribute, and is absent from the generated api.kt. Android and
iOS cannot call it. Real NAT traversal already runs through libp2p
dcutr/autonat/relay (core/src/transport/behaviour.rs:63-67).

So nat.rs is a parallel, vestigial, fake implementation -- exactly the kind of
orphaned code that misleads readers, audits, and agents.

DECISION: DELETE the fake path for 0.4.0 (about 200 LoC removed, plus the
IronCore wrapper). It removes a landmine and costs no capability, because
libp2p provides the real path. Do NOT port Freenet's ~800-LoC hole-punch into
this release -- introducing a new crypto handshake during a release freeze is
precisely how regressions arrive. HANDOFF/freenet-lessons-learned.md remains
the design of record for a post-0.4.0 effort; its measured baseline (64%
success, 200ms cadence over 3s, X25519 intro packets, handshake state machine,
asymmetric-decryption rate limit) is sound and worth doing later.

## 9. Adversarial review: what was accepted, and what was refuted

ACCEPTED:
- iOS-iOS mDNS regression risk -> switched the fix to dual-stack browsing.
- PR #128's history is poisoned -> cherry-pick fresh rather than hand-patch.
- BLE MTU asymmetry (Android ~512 vs iOS ~185) -> confidence downgraded;
  expect framing bugs after discovery succeeds.
- Deep-link listeners create a new attack surface -> validation added as a
  first-class requirement, not an afterthought.
- Do not introduce new crypto during the release freeze -> delete the fake
  hole-punch rather than port Freenet now.

REFUTED, with evidence:
- Claim: "removing the hardcoded relay may leave the CLI with zero bootstrap."
  False. cli/src/main.rs:53 only builds the APK-share display URL. The CLI's
  bootstrap lives in cli/src/bootstrap.rs (SC_BOOTSTRAP_NODES env :38,
  build-time option_env :49, merge :106) plus mDNS (config.rs:20-21).
- Claim: "Stage 3 absolutely depends on PR #128 because iOS links the Rust
  core." Overstated. The iOS 0.5.0 branches change nothing under core/, and
  #128 is not merged, so both sides already build from main's core. The genuine
  requirement is provenance match between the two builds, which Stage 3 now
  states explicitly.

NOTED BUT OUT OF SCOPE:
- Tailscale may have been someone's SSH-admin plan for the EC2 box. That is an
  infrastructure choice and does not make it a peer connectivity mechanism.
