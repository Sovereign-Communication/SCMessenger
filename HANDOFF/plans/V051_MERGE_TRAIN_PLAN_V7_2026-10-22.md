# SCMessenger v0.5.1 merge-train plan v2 (Overseer: Claude; Landing, Implementer: Freebuff lanes)

Goal: land every open PR (or close it with a recorded disposition) and tag v0.5.1 on a green main, publish only after a passing three-node real-device gate.

Roles: Landing is the only merger and never merges its own work. Implementer fixes red CI and never merges or reviews. The Overseer rules, spawns the independent security reviewer and runs the final gate. Nobody reviews or lands their own work; authorship follows the session.

Branch protection stays strict=true (PR must be up to date with main); no repository settings change.

Sequence: #597 (wasm test build fix) first; then #616 and the state-seed install; then batches. Batch A docs/tooling/CI; B dependabot actions and patch bumps; C android/ios; D core fixes touching routing/transport (#550 #556 #554 #509); E connection admission (#521 with its fix PR #599) alone; F release (version bump, docs sync, tag, gate). Dependabot major bumps (x25519-dalek 3.0, tower-http 0.7, kotlin 2.4, navigation-compose) are never in a batch: each lands alone after crypto/compatibility review or is closed with a recorded reason. Dead or superseded PRs are closed with recorded dispositions.

Batch construction: each batch is an integration branch of the member PRs using merge commits (authorship preserved), opened as ONE PR with ONE fresh full CI run on the batch head. Cancelled CI is unverified, never a pass; per-PR results are not reused. Every hand-resolved conflict hunk is listed in the batch PR body. A red member is bisected out and routed to the Implementer so it does not block the batch. Originals are closed "landed via #N" only after the batch merges green.

Merge gate (mechanical only): exact-head CI green on all required checks, no conflicts, and for core/src/{crypto,transport,routing,privacy}/ an APPROVE from an independent reviewer bound to that exact head SHA (a head move voids the verdict and re-requests review). Batches D and E also require NAT Simulation and the full test suite green on the batch head and again on main after merge. Jev is advisory only and never authorizes a merge; a Jev outage, escalate or fallback is no signal and means manual review.

Safety: one merge at a time; after every merge, wait for main's checks on the new head to finish green before the next merge. If main goes red, declare MAIN-RED, halt the queue, and revert via a revert PR of the batch merge commit (git revert -m1); never force-push. Rollback anchor: branch at pre-train main 657dc1365. No change to on-disk store format, wire format or FFI signature lands without an explicit compatibility note in the READY message; the revert path is checked against that note before merge. A flaky or cancelled job is rerun at most twice on the same head, then the train halts and reports; a failure rate above 20 percent in a batch pauses the train.

Resumability: at every step boundary the holding role writes a checkpoint (role, epoch, stage, PR, head SHA, resumed or new) to the journal. Before retrying any action (merge, push, comment, branch update) the role re-reads GitHub and skips the action if it already happened. Roles hold epoch-fenced leases; a role silent more than two hours with work pending is revoked and respawned. Escalations are complete packets (what is blocked, evidence, what was tried, what proceeds meanwhile) routed through the Overseer; owner-only items are money, credentials, branch deletion without 100 percent proof, and the live pilot.

Release: F-1 version bump, F-2 docs sync, tag v0.5.1 on the green main head, then the Reviewer runs the three-node real-device verification (sender decrypt, durable history and receipt on each node, never transport ACKs alone); publish only on a PASS verdict; a failed gate returns to the Implementer as a work item.

AMENDMENT 1 (speed): CI waits are overlapped, never idle. While batch N is in CI or in its post-merge main verification, Landing prepares batch N+1 as an integration branch, the Implementer fixes red members and rebases cancelled-CI members, and the independent reviewer reviews the combined head of the next protected-path batch. Batch N+1 receives a mechanical update-branch from main only at its turn; because main then contains only the previous batch, a security verdict on the pre-update head is carried forward by a delta review of the update (git diff between the reviewed head and the new head), and a full re-review is required only if the delta touches core/src/{crypto,transport,routing,privacy}/ or a file the batch itself changed. Batch A is split into A1 (docs/tooling, no code) and A2 (CI workflows) so the first merge happens within one CI cycle and every later batch starts from a known-good main. Within any batch, members are grouped by file overlap so conflicts surface during preparation, not at merge time. Target: at most six batch CI cycles for about thirty PRs, with no cycle spent waiting on a human decision; a cycle that sits idle more than 15 minutes with work pending is reported by Landing to the Overseer.

AMENDMENT 2 (safety): Every known failure mode has a detection, an owner and a recovery. Cancelled or stale CI: detected by check-run conclusion on the exact head, owner Landing, recovery fresh run (two reruns max). Moved head after a verdict: detected by comparing verdict SHA to head SHA, owner Landing, recovery re-request review or delta review. Hand-resolved conflict error: detected by the conflict-hunk list in the PR body checked by the reviewer, owner Landing then reviewer. Dependency change: for every dependabot batch Landing diffs the Cargo.lock and Gradle lock crate lists, requires cargo-deny and audit green, and records any new crate or major version; unknown new crates stop the batch. Landing's journal disagreeing with live GitHub: Landing trusts GitHub, journals the mismatch and stops the batch until it is reconciled. Reviewer unavailable or silent beyond two hours: the Overseer respawns it; no protected-path merge happens without a current verdict. Secret or credential found in any diff: the batch stops and the Overseer escalates; gitleaks must be green. Main red after merge: MAIN-RED, queue halted, revert PR of the batch merge commit, no new merge until main is green again. Unknown state of any kind is a stop, never a guess.

AMENDMENT 3 (rollback compatibility): Landing mechanically classifies every PR before batching: any change under the on-disk store modules, the wire protocol or message schema, the identity or key storage, or the FFI interface definitions is labelled format-changing. A format-changing PR must carry in its READY message either a statement that old data still opens (with the test that proves it) or a version-gated migration; it is merged alone or last in its batch, and its batch is not marked done until the revert path is checked: the reviewer confirms that reverting the merge commit leaves data written by the new version readable, or the batch is declared forward-only with the Overseer's recorded approval. The final real-device gate includes an upgrade-then-downgrade check: install the new build over existing data, send and receive on all nodes, then reinstall the previous build over the same data and confirm the message store still opens and delivers. The rollback anchor branch at pre-train main remains in place until the release is published.

MECHANICS CHECKED AGAINST THOSE FACTS. Merge-commit batches are allowed (allow_merge_commit=true) and linear history is not required, so a batch PR can be merged with a merge commit and reverted with git revert -m1 on that merge commit. Because the batch merge brings each member PR's head commits into main, GitHub marks member PRs merged automatically when their heads are reachable from main; any member that does not auto-close is closed by Landing with the comment "landed via batch PR". delete_branch_on_merge=true deletes only the merged batch branch; member branches and all backup/* and preserve/* refs are never deleted by this plan. strict=true is satisfied for a batch because Landing runs update-branch immediately before the batch's fresh CI cycle, and the batch is merged only if main has not moved since; if main moved, the batch is updated and re-verified, which is the head-guard. Required checks are only the five listed, so the batch PR can merge once those are green, but this plan additionally requires every non-required check that the member PRs normally run (NAT Simulation, Full Test Suite, FFI Surface Contract, Forgery/Negative Security Regression) to be green on batch heads that touch code. A revert PR of a batch merge commit goes through the same required checks; if main is red the revert PR is the priority-zero item.
